## Agreed workflow

```text
TODO
  └─ Enter a prompt; no stage choice
       ↓
IN PROGRESS — one unified agent work run in the isolated task worktree
  ├─ No uncheckpointed code changes → show the agent's ordinary final response
  └─ Changes exist → Live shows Changes to review card
       ↓
REVIEW — inspect summary, changed files, and diff since latest checkpoint
  ├─ Cancel → preserve the worktree; no commit and no discard
  └─ Confirm Update checkpoint → commit exactly the previewed file state (not a code-review attestation)
       ↓
Sync with main — merge the latest primary-branch tip into the task branch
  ├─ No conflicts → continue
  └─ Conflicts → preserve Git state; user resolves and commits in the IDE, then continue
       ↓
Check sync — verify Git ancestry and safe worktree state (not application tests)
       ↓
User opens/runs/tests the app in the task worktree
       ↓
Explicit Merge back — repeat final safety checks; integrate task branch to main
       ↓
DONE / MERGED
```

`Mark as done without merging`, if retained, stays a separate `DONE / CLOSED` outcome.

## Product rules and safety invariants

- New work has one internal work-run kind. The user supplies a prompt; the task description and prompt guide the agent. Do not ask the user to classify the work as Investigation or Implementation.
- The work agent can modify files in the isolated task worktree. The explicit diff review and checkpoint confirmation—not a read-only Investigation mode—control what becomes a checkpoint.
- No code changes means no special handover/card: retain and display the agent's ordinary final response in Live.
- If changes exist, the card summarizes the run using its ordinary final response (shortened for display), lists changed paths, and previews the actual diff from the latest checkpoint through the current worktree. A separate mandatory handover document is not part of this plan.
- The diff includes tracked, staged/unstaged, deleted, renamed, and untracked changes. Never stage or commit anything merely to build a preview. Never silently discard changes.
- The checkpoint confirmation is bound to the exact branch, HEAD, changed-file set, and worktree state shown to the user. If anything changes after preview, refuse and require a fresh preview.
- Sync is an explicit merge of the current recorded primary base into the task branch; it is not merge-back. Never auto-resolve conflicts. Preserve conflict markers, index entries, and user edits until the user resolves/commits or explicitly aborts.
- Check sync verifies the expected task branch, clean worktree, no Git operation in progress, and that the **current** base tip is an ancestor of the task HEAD. Use commit ancestry, not commit dates.
- Check sync is a Git-state check only. It does not run the app or claim functional correctness. If the base moves after the check, the check is stale and must be repeated after syncing.
- Application testing and final code review are solely the developer's responsibility. Immediately before Merge back, show a clear reminder to test the app in the task worktree and review the implemented code. Do not require a checkbox/attestation; the reminder is not a technical test gate.
- Merge back requires a separate explicit user confirmation and final exact-ref/worktree checks. Preserve safe fast-forward/CAS behavior and the existing non-primary linked-worktree block.
- Keep old persisted runs, handovers, and Validation records readable unless a separate data-retention decision is made. Removing runtime behavior does not authorize deleting user history. The only approved exception is the current pre-deployment development database reset recorded below.

## W-12 Check sync result conditions

Check sync is an explicit, read-only, point-in-time Git check. It briefly acquires the shared task-operation lock and reports the checked base/task SHAs. It does not start or inspect a Pi session, create a task run, execute application tests, or claim code-review/merge readiness. Recheck after Git changes; a later base advance does not live-update an earlier result.

- **`IN_SYNC`** — The task is in Review and has base/worktree/expected-branch metadata; no other task operation or active sync-recovery attempt blocks the check; the task worktree is on the expected branch, clean, and has no Git operation or unmerged paths; its HEAD equals the recorded latest task checkpoint; the current base tip can be read; and Git confirms that current base tip is an ancestor of that task HEAD.
- **`STALE`** — Those structural/task-state conditions are safe, but Git confirms the current base tip is **not** an ancestor of the task HEAD. The response directs the developer to Sync with main and check again. This is the only non-blocked failure classification.
- **`BLOCKED`** — Any prerequisite is unsafe or cannot be verified: another task operation holds the lock; the task is not in Review; required base/worktree/branch metadata or a recorded checkpoint is missing; the task branch or HEAD differs from the expected/recorded value; the worktree is dirty; a Git operation or unresolved conflict is present; an active persisted sync recovery exists; the current base/worktree state cannot be read; or Git cannot determine ancestry (an ancestry command error other than “not an ancestor”). A missing task returns HTTP 404 rather than a status result.

`base_moved` is informational: it is true when the currently read base tip differs from the task's recorded `base_commit_sha`. That alone does not make the result stale if the current base tip is already an ancestor of the task HEAD; in that case the result can be `IN_SYNC` with `base_moved: true`. The displayed result identifies the SHAs and check time so it is not presented as a continuously refreshed guarantee.
